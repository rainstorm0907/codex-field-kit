# Frontend Creation

Create the experience from the person's purpose and real material. These sections guide decisions, not ten sequential gates. Product, permission, accessibility, platform and release contracts still bind. Read a specialist only for a decision it can improve; reuse guidance already in context.

## 1. Frame the path

Inspect the request, artifacts, routes and existing product before asking the user to repeat discoverable facts. For each affected role, make the first view answer what matters now, which objects need their attention and what they can do next. A viewing or exploratory surface may need orientation rather than an action.

Borrow familiar working order: finding a relevant item, examining its evidence, making a decision and continuing. Copying tabs or form styling does not establish that order. Separate surfaces when the actor's purpose or working context changes; do not turn every process step into a page. Keep required evidence beside the work and let people revisit earlier decisions.

Distinguish required behavior from your chosen layout. Keep a brief in existing notes only when coordination or resumption needs it. Before delegation, connect the intended scene to behavior that can actually produce it. Exploration does not authorize publication or unrelated product changes.

## 2. Real limits

Only user, product, platform and accepted work boundaries create hard limits. A layout budget cannot justify deleting approved content. Dense tools can need many controls; a viewing surface may need none. Resolve a real conflict with a specific recommendation. Preserve explicit freezes and permissions, including when changing a previously accepted baseline.

## 3. Compose content and hierarchy

Choose real content before arranging components. Comparison needs comparable states, editing needs the editable object, and motion needs timing. Counts orient; they cannot replace the evidence a decision requires. In a work queue, surface relevant unfinished work, incoming responses and changed evidence instead of giving every row identical priority. Apply those signals to every relevant status, including deferred items.

Distinguish repetition from different necessary information before cutting. Keep the actual work visible at the intended viewport; accumulated headers and notices must not consume its working space. Put internal diagnostics in working records unless the audience uses them. Match each visible claim to evidence of that scope; an official source does not prove a newly combined conclusion. Identify sample values as samples.

For review, labeling, comparison, moderation, generated evidence, synchronized media, private encodings, multi-role records or versioned results, read `task-evidence-design.md` for the relevant relationships. Do not load it for unrelated cosmetic edits.

## 4. Copy rules

A string should orient, identify content, explain an action or state, or enable recovery. Remove production rationale and repeated self-description while preserving useful failure messages and input-loss warnings. Technical identifiers may belong in an expert tool; ordinary users need recognizable objects and actions.

Use one product voice. For Korean copy or a new visual language, follow the project's explicit rules and the applicable defaults in `portable-design-principles.md`; read it once when needed. Preserve source text, real names and required wording. Do not turn awkward examples into a global word blacklist or a whole-repository symbol checker.

Changing words must preserve speaker, timing, causality and certainty. “예정입니다” cannot become “확인됐습니다” merely to sound cleaner. Headings and nearby context should identify whose information, which object and which version matter here, without forcing all three into every title. If labels need paragraphs to explain the task, inspect the missing context or scene.

Visible status must describe what happened. “저장했습니다” requires actual storage; a selection or accepted generation request is not a saved or completed result.

## 5. Visual concept

Use examples to understand relationships that improve reading, comparison or feeling. Bring over a relationship only when its conditions fit; a before/after layout requires a real change. Apply the portable judgment and emphasis defaults when relevant, without importing another product's tokens or screen contracts.

Make a coherent whole when judging the experience, and hold other conditions stable when testing one variable. A preserved comparison baseline is not a freeze. Candidate counts, generated-image approval and mixing favorite parts are not mandatory. When direction is delegated, deliver a reasoned candidate rather than requiring the user to choose each detail.

Use a medium that exposes the uncertainty and is allowed in this environment. Crop or recompose an available image before requesting another; label reconstructed mockups. Still images cannot prove timing or interaction. Apply §9 when live observation is restricted.

## 6. Model interaction and reachable states

For each reachable state, connect the trigger, visible meaning, action and recovery. Loading, empty, error, permission and offline states are possibilities, not a compulsory inventory. Keep uncertainty distinct from failure.

- Give a control one clear user intention. Do not make “generate” silently approve, change a decision or publish. Internal steps needed for the named action need not become separate buttons.
- Separate selecting several items from opening one. Pointer targets, labels and keyboard behavior must not trigger both actions together.
- Make prerequisites discoverable before execution, with the reason and a way to enter or save the missing information at that point. Do not invent another person's identity or change a valid decision to unlock an action.
- If conditional steps disappear, renumber visible steps or use descriptive names without numbers. Do not insert empty steps or impose a wizard merely to preserve numbering.
- Derive labels, dirty state, enabled actions and feedback from current state. Undoing a choice or returning to the saved value must restore the corresponding copy and controls. Scope feedback to the current person, object and version; an earlier item's success must not imply this item's completion.

## 7. Implement the complete path

Use semantic structure, accessible names, visible labels, logical focus, keyboard operation and readable contrast. Preserve safe input across recoverable failures and navigation, show consequential feedback, and respect reduced motion. Preserve filters and working position when returning to a queue. Responsive changes follow content and task, not a device-name checklist. Preserve required storage, permission and release behavior.

## 8. Removing clutter

Remove duplicate explanation or establish hierarchy among necessary parts. Useful evidence and deliberate expression can deserve space without being controls. Preserve the job of a removed element another way when still needed. Do not add a quota, inventory or unsolicited feature to prove simplification.

## 9. Render and walk the path

Observe the changed property and coupled behavior from a realistic state. For interaction changes, use the control and observe feedback, relevant recovery and resume. Check affected focus, text wrapping, clipping, contrast, browser errors and viewport behavior. A static image cannot prove a dynamic relationship, and code or build checks are not visual observations. Reuse evidence only while its target and dependencies remain valid.

After a material change to roles, flow, prerequisites or status, choose a representative screen and action for each affected role. This is a small checkpoint, not another full audit or approval gate. In the existing record, keep role, route/state, what to try, observer, actual observation time, result and an allowed evidence reference. Before observation, mark it pending; do not prefill an observation time. Avoid extra logs for unrelated minor polish.

When detailed screen checks are batched by the user, retain these checkpoints with the agreed observer and next check occasion. Do not translate “later” into “unnecessary,” and do not override an explicit request to defer. At that occasion, bring the pending role paths back before reporting visual completion. Check changed nonvisual behavior within the permitted scope in the meantime.

In a restricted environment, apply AGENTS.md's `제한된 작업 환경` rules: the user operates the platform's built-in Browser preview. Give the actual server port, route and a short action to try. Computer Use, external direct browsing and workaround tunnels are not substitutes. Attach a screenshot only when a permitted capture facility is confirmed; otherwise record the user's reported observation and time. Do not request prohibited capture shortcuts, upload personal files or claim the model saw an unseen screen. If no observation returns, keep visual verification pending and report the concrete gap.

Fix inspectable in-scope defects before handing them back for diagnosis. An explicitly assigned preview checkpoint may still conclude with disclosed gaps.

## 10. Fresh-eyes review

Use `fresh-eyes-review.md` when independent comprehension can resolve a material blind spot or the user/release contract requires it. Do not add a reviewer to every visual edit. Preserve staffing, model, budget and platform permissions.

A comprehension reviewer receives the actor and allowed rendered evidence before the builder's explanation. A goal reviewer also needs the actual goal and constraints. Neither certifies the user's taste. Code review or a report of somebody else's observation cannot be relabeled independent visual review.

Use supported findings for in-scope correction. A required review stays pending without valid evidence. Re-review only when required or changed evidence can change the decision, not to collect agreement.

## When to redesign instead of patch

If repeated local changes leave the same task confusion or create more explanation, revisit the role, evidence relationship or interaction model before further styling. A known local defect calls for a local repair. Counted rejections alone do not diagnose the cause. If an observation is unavailable, report that specific gap without inventing success or restarting everything.
